# Архитектура проекта ADDITIVE_LAB // GEN_01

## Обзор

Проект представляет собой **Client‑Side** (полностью работающее в браузере) веб‑приложение для параметрического 3D‑моделирования. Оно объединяет генеративный ИИ (для написания кода) и CAD‑ядро (для генерации геометрии) в едином интерфейсе: Python (SolidPython2) → OpenSCAD → STL → Three.js.

## Технологический стек

### Frontend (UI)

- **HTML5 / CSS3:** современный интерфейс без тяжёлых фреймворков (Vanilla JS).
- **CodeMirror:** встроенный редактор кода с подсветкой синтаксиса Python.
- **Three.js:** библиотека для 3D‑рендеринга (WebGL) для отображения STL‑моделей, орбиталей камеры и сетки.

### Compute (Ядро в браузере)

- **Pyodide (WebAssembly):** полноценный интерпретатор Python 3.11, работающий в браузере.
- **SolidPython2 (`solid2`):** Python‑библиотека, транслирующая Python‑код в OpenSCAD‑синтаксис.
- **OpenSCAD WASM:** порт ядра OpenSCAD на WebAssembly; выполняет CSG‑операции и экспортирует STL.
- **Web Workers:** вынос тяжёлых вычислений (рендеринг OpenSCAD) в отдельный поток для предотвращения зависания UI.

### AI (Искусственный интеллект)

- **OpenRouter API:** единый шлюз для доступа к LLM (Large Language Models).
- **Модели:** конфигурируемый список код‑ориентированных моделей (например, Gemini, Claude, GPT‑5.1‑Codex, Grok, специализированные coder‑модели).
- **Роль:** генерация валидного Python‑кода (SolidPython2) по текстовому описанию пользователя, с опорой на системный промпт и стратегии моделирования.

## Поток данных (Data Flow)

1. **Ввод:** пользователь вводит текстовый запрос (например, "Ваза с витой геометрией").
2. **AI‑генерация:**
   - запрос уходит в OpenRouter API с системным промптом;
   - AI возвращает Python‑код на SolidPython2;
   - код проходит предварительную валидацию (строки, скобки) и полную проверку синтаксиса через Pyodide (`compile()`).
3. **Транспиляция (Python → SCAD):**
   - код передаётся в **Pyodide** (main thread);
   - выполняется с использованием `solid2` и вспомогательных настроек (лимиты рекурсии, GC);
   - результат выполнения: строка с OpenSCAD‑кодом (`.scad`), сохраняемая также для скачивания.
4. **Рендеринг (SCAD → STL):**
   - SCAD‑код передаётся в **Web Worker** (`worker.js`) через класс `OpenSCADManager`;
   - Worker инициализирует/перезапускает OpenSCAD WASM;
   - OpenSCAD компилирует геометрию и экспортирует бинарный STL;
   - STL возвращается в main thread как `Uint8Array` (копия буфера для избежания detached‑проблем).
5. **Визуализация:**
   - **Three.js** парсит STL‑буфер;
   - создаётся `Mesh` с материалом, корректируются нормали;
   - рассчитывается `boundingBox`, центр модели и рекомендуемая позиция камеры;
   - камера и `OrbitControls` переориентируются на центр, отключается `frustumCulled` для предотвращения исчезновения модели при вращении.

## Ключевые архитектурные решения

### 1. Web Worker + OpenSCADManager

Рендеринг 3D‑моделей — ресурсоёмкая операция, склонная к ошибкам (CGAL, локализация, переполнения).  
Решения:
- использование выделенного `worker.js` для инициализации OpenSCAD WASM и запуска рендеров;
- класс `OpenSCADManager` в `script.js`:
  - инкапсулирует создание/перезапуск воркера;
  - для сложных задач может перезапускать воркер между рендерами, предотвращая накопление ошибок и утечек;
  - фильтрует лог‑сообщения из OpenSCAD и отделяет настоящие ошибки от информационных сообщений.

### 2. Resilient Rendering (устойчивый рендеринг)

OpenSCAD часто пишет в `stderr` предупреждения ("Could not initialize localization", статистика кэша и т.п.), которые не означают провал рендера.  
Подход:
- воркер собирает сообщения, но считает рендер успешным, если был создан и не пуст `output.stl`;
- только в случае отсутствия/пустоты STL формируется ошибка, которая возвращается в основной поток;
- критические состояния (краш воркера, "CRITICAL"‑сообщения) приводят к перезапуску воркера через `OpenSCADManager`.

### 3. Local-First

- Все тяжёлые компоненты (OpenSCAD WASM, патченный `openscad.min.js`, клиентский JS и стили) обслуживаются локально/статически.
- Pyodide загружается из CDN, но кэшируется браузером.
- Интернет обязателен только для AI‑генерации (OpenRouter). При этом уже сгенерированный и сохранённый код/SCAD/STL можно использовать без сети.

### 4. AI-пайплайн и валидация

- Перед выполнением Python‑кода выполняются:
  - статические проверки (баланс скобок, незакрытые тройные кавычки);
  - компиляция через `compile()` в Pyodide для точного обнаружения синтаксических ошибок и строк.
- AI‑ответ анализируется и очищается от markdown‑обёрток, обрезок кода, лишних префиксов.
- Обрабатывается `finish_reason` от OpenRouter: при `length` код считается потенциально обрезанным и помечается как проблемный.

### 5. 3D-просмотрщик и камера

- Используется `PerspectiveCamera` с увеличенным `far`‑параметром (до ~10000) для поддержки крупных моделей.
- Включён `logarithmicDepthBuffer` для уменьшения артефактов глубины на больших сценах.
- `OrbitControls` настроены с демпфированием (`enableDamping`), ограничениями по дистанции и плавными скоростями зума/вращения.
- При каждой новой модели:
  - рассчитывается `boundingBox` геометрии;
  - камера ставится на диагональ от центра на расстояние, обеспечивающее комфортный обзор;
  - `currentMesh.frustumCulled = false`, чтобы модель не исчезала при крайних положениях камеры.
- Известный UX‑нюанс: текущая реализация колеса мыши вешает `preventDefault` на `wheel` по канвасу, что блокирует скролл страницы — это зафиксировано как отдельный UX‑долг в `ROADMAP.md`.

### 6. AI-стратегии (дизайн, в разработке)

В соседнем десктоп‑проекте `OpenSCAD_AI` уже реализована идея **стратегий моделирования** (Organic Hull / Mechanical CSG / Lathe Rotate).  
В `ADDITIVE_LAB` архитектура AI‑слоя и промптов спроектирована так, чтобы:
- позволить добавление режимов в UI (селектор стратегии в AI‑панели);
- подмешивать стратегические блоки в system prompt для разных типов геометрии;
- при этом сохранить единый пайплайн валидации и исполнения кода.

Подробный план по стратегиям, мультимодалу (изображения как референсы) и UX описан в `ROADMAP.md`.
