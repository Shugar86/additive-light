# VibeCraft Engineering Rules: Личный Стандарт Разработчика

## 1. ФИЛОСОФИЯ: "Продукт > Код"

- **Принцип:** Мы создаем **"вайб"** — ощущаемый пользователем характер продукта. В CAD-Recode этот вайб выражается в детерминированности, надежности и предсказуемости. Главная задача — переводить требования к "вайбу" в конкретные инженерные решения.
- **Подтверждение:** Перед реализацией сложной бизнес-логики кратко сформулируй, какой вайб (`professional`, `deterministic`, `resilient`) ты будешь реализовывать. 

## 2. ПРИНЦИПЫ КОДА: "Прагматичный Senior"

- **LLMs reason. Deterministic tools decide:** Это фундаментальный принцип всей архитектуры. Никогда не используй LLM для расчета координат, радиусов, углов или проверки геометрии. Математику делают инструменты (Python скрипты: `numpy`, `trimesh`, `open3d`), LLM принимает решения о том, *какие* инструменты применить и *как* интерпретировать результат.
- **Читаемость — Приоритет №1:** Код должен быть **самодокументируемым**. Если для понимания функции нужен комментарий, значит, функция названа плохо.
- **Надежность > "Магия":** Используй **явные, проверенные паттерны**. Никаких метаклассов, глобальных переменных или неявных сайд-эффектов. Код должен работать предсказуемо и детерминированно.
- **YAGNI ("You Ain't Gonna Need It"):** **ЗАПРЕЩЕНО** писать код "на будущее". Реализуй **только то, что требуется** для текущей задачи.

## 3. ПРАВИЛА ГЕНЕРАЦИИ КОДА (Python)

1. **Версии — ТОЛЬКО АКТУАЛЬНЫЕ:**
 - Используй Python **3.11+**.
 - При добавлении любой новой библиотеки используй **последнюю стабильную версию**. Никакого легаси. Если зависимость требует старой версии другой библиотеки, **найди альтернативу**.

2. **Обработка Ошибок — ЖЕЛЕЗОБЕТОННО:**
 - **ЗАПРЕЩЕНО** использовать голый `except:`. Всегда лови **конкретные исключения** (например, `except ValueError:`, `except trimesh.exceptions.MeshError:`).
 - Для всех операций ввода-вывода (файлы, API), загрузки мешей и вычислений **ОБЯЗАТЕЛЬНО** используй `try...except` с **осмысленным логированием** ошибки (через `logger.error`). Система должна "падать" изящно и восстанавливаться в цикле рефлексии.

3. **Docstrings и Типизация — НЕ ОБСУЖДАЕТСЯ:**
 - **100%** кода должно быть покрыто **type hints** (включая `Optional`, `List`, `Dict`, `Any`).
 - Все публичные функции, классы и модули **ОБЯЗАНЫ** иметь **docstring в Google-стиле**.

4. **Тесты — ТВОЯ ОБЯЗАННОСТЬ:**
 - Для любой **нетривиальной бизнес-логики** (сенсоры, математика, парсеры) ты **ОБЯЗАН** предложить **каркас для `pytest`-теста**, покрывающего как минимум **успешный кейс** и **один провальный/граничный**. Тестируй инструменты, а не галлюцинации LLM.

## 4. ПРАВИЛА ОБЩЕНИЯ И АНАЛИЗА (Для Агентов-ассистентов)

1. **Стиль Ответа:** Кратко, по делу, структурировано. Сначала – **вердикт**, потом – **обоснование**.
2. **Объяснение Кода:** Фокусируйся на **компромиссах (trade-offs)**. "Я выбрал `Решение А`, потому что оно быстрее и детерминированнее, но менее гибкое, чем `Решение Б`. Для нашей задачи (CAD-Recode) детерминированность важнее".
3. **Предложение Рефакторинга:** Каждое предложение по рефакторингу должно сопровождаться **метрикой**, которую оно улучшает. "Предлагаю вынести этот расчет в отдельный сенсор, чтобы повысить **тестируемость (testability)** и **надежность (resilience)**".

## 5. ИЗОЛЯЦИЯ И БЕЗОПАСНОСТЬ (Security First)

Сгенерированный код (`build123d` скрипты, динамические навыки) — это untrusted input.
- **Обязательная AST валидация:** Запрещены опасные функции (`os`, `sys`, `subprocess`, `eval`, `exec`).
- **Изолированное исполнение (Sandboxing):** Выполнять только в отдельном процессе с установленным таймаутом (Time Limit).
- Система должна быть устойчива к бесконечным циклам (While True) в сгенерированном коде.
